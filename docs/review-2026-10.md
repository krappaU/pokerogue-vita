# Project review (2026-10-16)

A review of the repository at version 0.41 (commit 7a87aba), with the CI and tests added alongside
it. Everything marked "verified" was reproduced in this session (desktop runtime, the .vpk in
Vita3K, or a measurement); the rest is from reading the code and is marked as such.

## Summary
The project is in good shape for a one-person beta of an unusually hard port. The architecture
(a purpose-built "browser" around QuickJS-ng instead of a wrapper) is the right call and is well
documented: `docs/PLAN.md`, `docs/development.md` and the findings log explain not just what the
code does but why, with measurements. The C is consistent, terse and defensive about memory, and the
Vita-specific knowledge (OpenSSL entropy and lock exhaustion, vitaGL's quirks, Cg reserved words,
sampler arrays) is recorded where the next person will find it.

The main gap was verification: there were no automated builds or tests, and the native fast paths
were checked by hand with the probes in `runtime/scripts/`. That is now covered by CI (below). The
code findings are mostly about resources that are never released, plus a few sharp edges in the
build scripts.

## Strengths
- **Clear layering.** Platform (`platform_vita.c` / `platform_sdl.c`), engine host (`js_host.c`),
  web APIs in C (`gl.c`, `canvas2d.c`, `net.c`, `audio.c`) and in JS (`js/*.js`). The same code
  builds for the desktop, so nearly all work can be done headless in Docker.
- **Never patches the game.** Phaser adjustments hook `window.Phaser` as it is assigned
  (`js/bootstrap.js`), and each fast path falls back to Phaser's own code for anything unusual
  (cropping, custom pivots, masks, overridden pipelines).
- **Fast paths are checked against Phaser.** The `probe_verify_*` probes compare vertex data, uniform
  calls and draw calls frame by frame. They now run in CI on a Phaser scene (`runtime/tests/phaser/`).
- **Off-main-thread work done carefully:** network, image decoding and audio run on separate cores,
  with priorities chosen from measured stalls; the request lifecycle in `net.c` is documented.
- **Reproducible third-party code:** pinned tags and commits in `fetch_deps.sh`, patches kept in
  `runtime/patches/`, nothing vendored.
- **Diagnostics built in:** the `[perf]`/`[mem]` log lines, the watchdog, the sampling profiler, the
  control channel and `debug.js` make problems on the console debuggable from a log file.

## Findings

### Fixed in this branch
1. **Every texture upload left a GL error on the Vita (verified).** vitaGL's `glPixelStorei`
   accepts only `GL_UNPACK_ROW_LENGTH` and raises `GL_INVALID_ENUM` for anything else
   (`vitaGL/source/textures.c`), and `gl.c` set `GL_UNPACK_ALIGNMENT` before every upload. It had no
   visible effect, but `glGetError` always reported an error, which hides real ones. Fixed with
   `gl_pixel_store()` in `src/gles.h` (commit 617ff9e); found by the new Vita3K tests.
2. Shellcheck warnings (a bare `cd` in three scripts), so lint can run at warning level.

### Should fix
3. **Phaser's framebuffer cleanup never frees its renderbuffers (verified).**
   `getFramebufferAttachmentParameter(..., FRAMEBUFFER_ATTACHMENT_OBJECT_NAME)` returns an integer
   (`gl.c`, `w_getFramebufferAttachmentParameter`), but WebGL returns the attached
   `WebGLTexture`/`WebGLRenderbuffer` object or `null`. Phaser's `WebGLFramebufferWrapper.destroy()`
   passes that value to `deleteRenderbuffer`/`deleteTexture`, which ignore anything that isn't one
   of the runtime's GL objects (`oid()`). Measured on the desktop runtime with Phaser 3.90: 54
   renderbuffers created during start-up, five resizes and five RenderTextures; 47
   `deleteRenderbuffer` calls, **none of which deleted anything**. Depth/stencil renderbuffers are
   the size of their render target, so this is GPU memory that is never freed. How much it costs in
   PokeRogue depends on how often the game creates and destroys render targets; a `[mem]` log over a
   long session would show it. Fix: track id → object and return the object (or `null`). On vitaGL,
   only `COLOR_ATTACHMENT0` is supported, and its "name" is a pointer to vitaGL's framebuffer struct,
   not a texture id, so the runtime should answer from its own record of what it attached
   (`framebufferTexture2D`/`framebufferRenderbuffer`) instead of asking vitaGL. Phaser's call for the
   depth/stencil attachment is also what raises the remaining `GL_INVALID_OPERATION` at start-up.
4. **The HTTP disk cache is never cleaned (read).** `<data>/http/` keeps every versioned asset and
   chunk forever (`net.c`, `cache_write`); each game release adds new hashed chunks, and nothing
   deletes the old ones (the bytecode cache, by contrast, drops files older than 14 days). Over
   months this fills the memory card. Suggest the same age-based cleanup, using the file's access
   or modification time (touch on hit).
5. **A missing shader compiler quits without a message (verified in Vita3K).** Without
   `libshacccg.suprx`, `plat_init` logs a line and `main` returns 1: the app closes back to
   LiveArea, and the explanation is only in `log.txt`. This is likely the most common first-run
   problem for new users. The message could be drawn without vitaGL (straight to a framebuffer with
   `sceDisplaySetFrameBuf` and the 8x8 font already in `third_party/`) and wait for a button.
6. **The build scripts can report success on a failed build (read).** `build_linux.sh` pipes the
   compiler through `grep` and then only checks that `build-linux/pokerogue-rt` exists;
   `build_vita.sh` ends with `; true` and checks that the .vpk exists. After a compile error, a
   binary or .vpk from an earlier build passes these checks, so the next test or install uses old
   code. CI is not affected (it always builds from scratch). Suggest `set -o pipefail` inside the
   `docker run` commands, or deleting the outputs before building.

### Worth verifying
7. **Shader identifier renaming doesn't rename lookups (read).** `js/webgl.js` renames Cg reserved
   words (`texture`, `matrix`, `half`, `get`, `shared`, ...) everywhere in shader sources, including
   uniform and attribute names, but `getUniformLocation`/`getAttribLocation`/`bindAttribLocation`
   and the names returned by `getActiveUniform`/`getActiveAttrib` aren't mapped. A uniform or
   attribute named, for example, `matrix` would silently get location -1/null. Phaser's and today's
   PokeRogue's shaders avoid these names, so this is latent; mapping the names (as is already done
   for sampler arrays) would close it.
8. **Unpinned inputs make builds drift (read).** `vitasdk/vitasdk:latest`, Vita3K's rolling
   "continuous" build, the `cacert.pem` fallback to the latest bundle, and `debian:bookworm` /
   `ubuntu:24.04` without digests. A broken upstream release shows up as a CI failure with no code
   change. Pinning the VitaSDK image by digest matters most (it builds the shipped .vpk).
9. **Offline install isn't verified before replacing the old game (read).** `offline_install`
   deletes the installed `game.zip` and renames the download into place without checking it against
   the release's `size` (already parsed) or that it opens as a zip. HTTP 416 is also treated as
   "already complete". A size check before the rename would keep a bad download from replacing a
   working game.

### Minor (read)
- `control_poll` waits forever on a control-file line longer than 8 KB (treated as partial).
- `evalfile` (control channel) and `cache_read` don't check `malloc`/`ftell` results.
- `mallinfo` is deprecated in glibc (desktop build warning); `mallinfo2` there, `mallinfo` on the Vita.

## Tests and CI (added)
`.github/workflows/ci.yml` runs on every push and pull request:

| job | what | time |
|---|---|---|
| lint | `scripts/lint.sh`: `node --check` on all JS, shellcheck, SPDX headers, VERSION, no Sony modules committed | 10 s |
| linux | `build_linux.sh`, then `scripts/test_linux.sh`: `tests/smoke` (23 checks of the browser shim) and `tests/phaser` (the three `probe_verify_*` probes on a Phaser 3.90 scene) | 1.5 min |
| vita | `build_vita.sh`; the .vpk is uploaded as an artifact for every commit | 4.5 min (libcurl/vitaGL cached after the first run) |
| vita3k | boot check without the shader compiler, then both test pages on the emulated Vita | 2 min |

Both test pages pass on the desktop runtime and in Vita3K (verified locally and in CI run
[38875805528](https://github.com/krappaU/pokerogue-vita/actions/runs/38875805528), about 7 minutes in all). The tests
were checked to catch regressions: a one-character change to `btoa`, a 1 px vertex change in the
container renderer and a changed uniform value each fail them.

Limits: Vita3K doesn't write its rendering back to the Vita's memory (`readPixels` returns zeros),
so pixel output is only checked on the desktop; text isn't drawn in the tests (no font is loaded);
nothing exercises the live site, logins or the real game, which would need the offline build
(~530 MB) or network access CI shouldn't depend on.

## Suggested next steps
1. Fix finding 3 (renderbuffer leak) and check `[mem]` lines over a long session on the console.
2. Findings 4-6: cache cleanup, a visible message for a missing shader compiler, honest build scripts.
3. Grow the tests with the code: a check in `tests/smoke` for each new web API, a scene element in
   `tests/phaser` for each new fast path. Candidates now: savecrypt (native AES against crypto-js,
   as `probe_savecrypt.js` does), the zip-backed offline mode, MP3/M4A decoding, a loaded font so
   text is drawn.
4. A scheduled (weekly) job that runs the offline game build in the desktop runtime to the title
   screen and checks the log for `[missing]` APIs and uncaught errors: an early warning when a new
   PokeRogue release needs something the shim lacks (risk 4 in `docs/PLAN.md`).
5. Pin the VitaSDK image by digest and record it in `docs/development.md`.
